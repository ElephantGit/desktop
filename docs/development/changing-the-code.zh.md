# 修改代码

[English](changing-the-code.md) | 中文

从拥有这件事的用例出发，而不是从改动文件的数量出发。DTO、生成产物、测试和文档是不同的类别；改动的文件多，本身并不意味着事实被
重复了。这些步骤背后的原则（单一事实来源、领域归属、最小接口、生命周期与隔离、行为验证）写在 `AGENTS.md` 中。

## 给已有领域添加一个操作

手写的事实有四个：**契约**、**逻辑操作**、**Desktop 绑定**和**业务实现**。其他一切都由它们生成或组合而来。

1. **契约。** 在所属的 `crates/contracts/src/<domain>.rs` 中定义请求和响应 DTO，并在该模块的 `export` 函数中登记它们的
   TypeScript 导出。DTO 模块的文件名使用 kebab-case（`#[ts(export_to = "workflow-run.ts")]`）。不要把传输路由和 Webview 授权
   放进 DTO。真正新的 DTO 族还需要它自己显式的模块和导出组合条目。
2. **逻辑操作。** 加在 `xtask/src/frontend/namespaces/<namespace>.rs` 下，写明操作名、客户端命名空间和成员、DTO 名称，以及显式
   的 `FrontendResponseMode::Unary` 或 `Stream`。
3. **Desktop 绑定。** 加在 `apps/desktop/src-tauri/bindings/` 下。单次请求的绑定指明它的 Rust 处理函数和 `Permission`；流式绑定
   指明一个领域的启动处理函数，并复用经过授权的 `stream_contract`/`cancel_contract_stream` 这一对。没有 SDK 操作的原生命令也属于
   这个目录。
4. **实现。** 在领域模块中实现用例。Backend 操作使用一个窄的领域句柄：不要在根 `Backend` 上添加转发方法，也不要暴露存储、锁或
   监督者。Desktop 适配层通过共享的请求生命周期辅助函数调用句柄；文件流的启动属于 `commands/files.rs`，`StreamStart` 负责登记、
   取消、启动结算和转发。
5. **生成。** 运行 `task export-contracts`，再运行 `task check:contracts`。永远不要手改客户端转发、DTO barrel、传输映射、流
   分发、命令注册或权限。重复生成以验证结果确定；检查从不修复漂移，也不删除未知的手写文件。
6. **测试**要在操作真实的接口上进行：当 SQLite 和 Git 正是被测行为时，Backend 测试保留真实的 SQLite 和 Git；前端测试使用生产
   客户端加带类型的处理函数。验证 DTO 和选项的传递、带请求 id 的错误以及生命周期结果；流还需要消费、中止或卸载以及清理的证据。
7. **验证**先用最小的相关任务，再跑包级检查。Desktop 的改动需要 `task test:tauri`，横跨多处的改动需要 `task test`。见
   [测试](testing.zh.md)。

## 前端归属检查清单

- 翻译留在所属的功能里；只有出现新的 owner 时才在根组合中添加资源。key 对齐和重复检查必须通过。
- 共享的剪切、复制、粘贴和全选文案属于 `features/editor/translations.ts`；Chat 专用的文案留在 Chat。
- 查询身份、权威响应的采用和失效属于 `state/data/` 下的数据 owner。保留有意义的 key 区分、删除级联和事件刷新范围；UI 不能复制
  query key 字符串。
- 在 `interface.json` 中只声明其他功能需要的公开符号，并写明用途。共享状态不能依赖功能 UI。
- 显式组合测试用的内存适配器；缺少的操作必须失败。
- 确定每个 watcher、事件桥、定时器、observer 和原生界面由谁拥有，并在范围变化、卸载和关闭时释放它们。

见[前端架构](../core/frontend-architecture.zh.md)。

## 删除一个功能

1. 先找出它的公开使用方和持久数据。删除功能从不意味着可以删除用户文件，本地文件系统布局是硬性的兼容边界：如果旧路径可能与新
   布局冲突或妨碍安全启动，先设计检测、迁移或隔离。
2. 删除它的实现、DTO 和导出条目、逻辑目录条目、Desktop 绑定、过时的组合、接口声明和翻译。不要保留根上的转发或第二套实现作为
   兼容层。
3. 通过各自的领域接口更新使用方。对于共享数据，检查其他 owner 是否仍需要查询工厂和失效策略。停止订阅，删除功能自己拥有的缓存和
   草稿状态，但不要清掉其他 Workspace 的状态。
4. 重新生成。删除的操作必须从生成的客户端、路由、DTO 导出、注册和权限中消失；检查已跟踪的差异和未跟踪的生成文件，并分别确认
   主 Webview 和插件 Webview 的能力。
5. 把仍然存在的职责对应的测试一起移走，只有当行为被有意删除或已在别处直接覆盖时，才去掉对应的测试义务。
6. 搜索旧的操作名、import、query key、翻译 key 和夹具。运行生成、功能接口和 Rust 大小检查，删除过时的大小例外，并更新受影响的
   文档。

按类别审查最终的 diff：实现和声明、必要的组合、生成产物、测试和文档。

## 文档

当改动新增或改变了行为时，在同一个改动中更新 `docs/` 下对应的文档，两种语言版本都要更新，遵循[维护规则](../README.zh.md#维护规则)。
`specs/` 是独立的仓库；修改其中的 ADR 遵循它自己的说明。
